# МойДом — цифровой сервис управления многоквартирным домом

## 1. Назначение решения

«МойДом» — цифровой сервис для жителей многоквартирных домов, ТСЖ и управляющих организаций.

Решение предназначено для демонстрации и тестирования цифровых сервисов управления многоквартирным домом в формате веб-приложения, адаптированного под использование в мини-приложении мессенджера MAX.

Основные задачи решения:

- просмотр начислений и услуг ЖКУ;
- работа с показаниями и расчётами;
- просмотр информации о состоянии инженерных систем дома;
- просмотр интерфейса видеокамер подъездов;
- создание заявок в аварийно-диспетчерскую службу;
- прикрепление фотографии к заявке;
- общение жителей в общедомовом чате;
- публикация официальных сообщений ТСЖ;
- участие жителей в голосованиях;
- демонстрация тестовой оплаты через СБП;
- предоставление REST API для проверки работы системы.

Решение рассчитано на демонстрационный/MVP-сценарий и использует тестовые данные без подключения к реальным лицевым счетам, банковским счетам и физическим камерам многоквартирного дома.

---

## 2. Основной пользовательский сценарий

1. Пользователь открывает веб-интерфейс приложения.
2. Система загружает демонстрационные данные квартиры:
   - лицевой счёт: `4181-7810-0008`;
   - адрес: г. Белгород, проспект Славы, дом 8;
   - квартира: 8.
3. Пользователь открывает раздел «Счета».
4. Просматривает начисления и доступные услуги.
5. При необходимости добавляет тестовую услугу или вводит объём/показания.
6. Нажимает кнопку оплаты.
7. Система переводит счёт в тестовое состояние `paid: true` и формирует тестовый номер чека.
8. В разделе «Дом» пользователь просматривает состояние инженерных систем и интерфейс видеокамер подъездов.
9. Через центральную кнопку «+» пользователь создаёт заявку в аварийно-диспетчерскую службу и может прикрепить фотографию.
10. В разделе «Чат» пользователь отправляет сообщение жителям дома.
11. В разделе «Опросы» пользователь просматривает доступные голосования и может принять участие в активном опросе.
12. При необходимости пользователь нажимает кнопку сброса и возвращает демонстрационную систему в исходное состояние.

```text
│

```

### Frontend

`frontend/` — клиентская часть приложения.

Используемые технологии:

- React 19;
- React DOM;
- Vite;
- Lucide React;
- Nginx.

Frontend собирается в production-сборку с помощью Vite и после сборки обслуживается веб-сервером Nginx.

### Backend

`backend/` — серверная часть приложения.

Используемые технологии:

- Python 3.11;
- FastAPI;
- Uvicorn;
- Pydantic;
- HTTPX;
- python-multipart.

Backend предоставляет REST API для работы с:

- начислениями;
- оплатой;
- информацией о доме;
- заявками;
- чатом;
- голосованиями;
- сбросом демонстрационных данных.

### Docker Compose

`docker-compose.yml` объединяет frontend и backend в единое локальное решение.

Запуск обоих компонентов выполняется одной командой.

### DATA-API.yaml

`DATA-API.yaml` содержит формализованные проверки основных API-методов и ожидаемых структур ответов.

### OpenAPI

`openapi.yaml` — формальное описание REST API в формате OpenAPI 3.1.

Файл содержит:

- адрес API;
- доступные endpoint'ы;
- HTTP-методы;
- query-параметры;
- path-параметры;
- HTTP-заголовки;
- тела запросов;
- схемы данных;
- ожидаемые HTTP-коды;
- структуры ответов.

### Тестовые данные

`test-data/` содержит данные, необходимые для воспроизводимой проверки API.

`accounts.yaml` — тестовые учётные записи и роли пользователей.

`test-data.json` — тестовые данные дома, лицевого счёта, заявок, чата и голосований.

`verify_api.py` — автоматизированный скрипт проверки основных API-сценариев.

## 4. Одна команда для запуска всех локальных компонентов через Docker

Для запуска всего решения необходимо находиться в корневой папке проекта и выполнить:

```bash
docker compose up --build -d
```

После успешного запуска:

- Frontend: `http://localhost:3000`
- Backend API: `http://localhost:8000`
- Swagger-документация API: `http://localhost:8000/docs`

---

## 5. Необходимые параметры окружения

Для стандартного локального демонстрационного запуска внешние параметры не являются обязательными.

Используются следующие параметры:

```text
MAX_BOT_TOKEN
VITE_API_ORIGIN
```

Секретные значения токенов и идентификаторов не храняться в `README.md`, Git-репозитории или исходном коде.

---

## 6. Переменные окружения

### MAX_BOT_TOKEN

Токен бота/команды для интеграции с платформой MAX.

Пример:

```text
MAX_BOT_TOKEN=your_token_here
```

Фактическое значение токена в репозитории не хранится.

### VITE_API_ORIGIN

Адрес backend API, который используется frontend при сборке.

Для локального Docker-запуска:

```text
VITE_API_ORIGIN=http://localhost:8000
```

При облачном размещении значение указывает на HTTPS-адрес развернутого backend. (https://myhome-eqju.onrender.com)

## 9. Внешние сервисы и интеграции

### MAX

Приложение предусматривает работу в экосистеме мессенджера MAX.

Предусмотрены:

- интеграция с Bot API;
- использование WebView / мини-приложения;
- идентификатор тестового чата;
- токен бота.

В локальном демонстрационном режиме приложение может работать без фактического подключения к MAX.

### ГИС ЖКХ

Архитектурой предусмотрен сценарий интеграции с данными ЖКХ.

В текущей демонстрационной версии реальные запросы к ГИС ЖКХ не выполняются. Начисления и сведения о доме представлены тестовыми данными.

### Система быстрых платежей

Предусмотрен сценарий оплаты через СБП.

В текущей версии операция является демонстрационной и не приводит к реальному списанию денежных средств.

### Видеонаблюдение

Интерфейс предусматривает работу с видеокамерами подъездов.

В демонстрационной версии реальные RTSP/HLS-потоки камер не подключены. Используется интерфейс-эмулятор видеопотока.

## 10. Описание работы с данными

Backend хранит демонстрационное состояние приложения в оперативной памяти процесса FastAPI.

К таким данным относятся:

- информация о платёжном документе;
- список услуг;
- состояние оплаты;
- заявки жителей;
- сообщения чата;
- результаты голосований;
- состояние демонстрационного дома.

Внешняя база данных в текущей версии не используется.

### Фотографии заявок

Прикрепляемые фотографии заявок сохраняются локально в:

```text
backend/uploads/
```

### Сброс данных

API предоставляет endpoint:

```text
POST /api/reset
```

Он возвращает демонстрационное состояние приложения к исходным тестовым данным.

## 11. Порядок работы с тестовыми данными

Для проверки используется демонстрационная квартира:

```text
ID: flat_8
Квартира: 8
Дом: 8
Адрес: г. Белгород, проспект Славы, д. 8
```

В исходном состоянии доступны:

- тестовые начисления;
- услуги ЖКУ;
- информация о доме;
- сообщения ТСЖ;
- демонстрационные заявки;
- голосования;
- завершённое голосование с результатом 13 за и 7 против.

Тестовые данные предназначены исключительно для демонстрации и проверки работы приложения.

Для возврата системы в исходное состояние используется кнопка сброса в интерфейсе либо:

```text
POST /api/reset
```

## 12. Пошаговый сценарий проверки

### Шаг 1. Запуск

Выполнить:

```bash
docker compose up --build -d
```

Проверить состояние контейнеров:

```bash
docker compose ps
```

---

### Шаг 2. Проверка frontend

Открыть:

```text
http://localhost:3000
```

Должен открыться интерфейс приложения «МойДом».

---

### Шаг 3. Проверка backend

Открыть:

```text
http://localhost:8000/docs
```

Должна открыться Swagger-документация FastAPI.

---

### Шаг 4. Проверка счетов

1. Открыть раздел «Счета».
2. Проверить отображение тестового платёжного документа.
3. Добавить тестовую услугу.
4. Проверить изменение общей суммы.
5. Нажать кнопку оплаты.
6. Проверить появление тестового чека.
7. Проверить изменение статуса оплаты.

Основные API:

```text
GET /api/bill
POST /api/bill/items
POST /api/bill/pay
```

---

### Шаг 5. Проверка информации о доме

Открыть раздел «Дом».

Проверить:

- состояние инженерных систем;
- информацию о доме;
- информацию об отходах;
- блок видеокамер.

Переключить камеры подъездов с 1 по 5 и проверить изменение выбранного видеопотока.

API:

```text
GET /api/house
```

---

### Шаг 6. Проверка заявки

1. Нажать центральную кнопку «+».
2. Открыть форму заявки.
3. Заполнить описание проблемы.
4. Прикрепить тестовую фотографию.
5. Отправить заявку.
6. Проверить появление заявки в списке.

API:

```text
GET /api/requests
```

---

### Шаг 7. Проверка чата

1. Открыть раздел «Чат».
2. Отправить сообщение.
3. Проверить его появление в списке.
4. Проверить возможность удаления собственного сообщения.
5. Проверить, что чужое сообщение удалить нельзя.

API:

```text
GET /api/chat
POST /api/chat
DELETE /api/chat/{id}
```

---

### Шаг 8. Проверка голосований

1. Открыть раздел «Опросы».
2. Проверить завершённое голосование.
3. Проверить отображение результата 13 за и 7 против.
4. Открыть активный опрос.
5. Проголосовать.
6. Попытаться изменить вариант голосования.
7. Проверить сообщение о необходимости отменить текущий голос.
8. Отменить текущий голос.
9. Выбрать другой вариант.

API:

```text
GET /api/polls
POST /api/polls/{id}/vote
```

---

### Шаг 9. Проверка сброса

Нажать кнопку сброса в верхней части интерфейса.

После сброса проверить:

- первоначальные начисления;
- исходные сообщения;
- исходные заявки;
- исходное состояние голосований;
- первоначальное состояние оплаты.

Также можно выполнить:

```text
POST /api/reset
```

## 13. Примеры ожидаемого поведения системы

### Получение платёжного документа

Запрос:

```http
GET /api/bill
```

До оплаты:

```json
{
  "paid": false
}
```

После успешной тестовой оплаты:

```json
{
  "paid": true
}
```

---

### Добавление услуги

Запрос:

```http
POST /api/bill/items
```

После выполнения возвращается обновлённый список услуг и новая общая сумма.

---

### Тестовая оплата

Запрос:

```http
POST /api/bill/pay
```

Ожидаемый результат содержит:

```text
paid
receipt_label
total_sum
```

Оплата является демонстрационной и не списывает реальные денежные средства.

---

### Ограничение изменения голоса

При попытке повторно проголосовать без отмены предыдущего голоса система возвращает HTTP `400`.

Ожидаемое сообщение:

```text
Сначала отмените текущий голос, чтобы выбрать другой вариант
```

---

### Удаление чужого сообщения

При попытке удалить сообщение другого пользователя система возвращает HTTP `403`.

Ожидаемое сообщение:

```text
Удалять можно только свои сообщения
```

---

### Сброс

Запрос:

```http
POST /api/reset
```

должен вернуть результат успешного выполнения операции и восстановить исходные тестовые данные.

---

## 14. Известные ограничения

1. Система использует демонстрационные данные и не подключена к реальным лицевым счетам жителей.
2. Состояние основных данных хранится в оперативной памяти backend.
3. После полного перезапуска backend состояние может вернуться к исходным демонстрационным данным.
4. Реальное списание денежных средств через СБП не выполняется.
5. Реальные камеры многоквартирного дома не подключены.
6. RTSP/HLS-потоки в текущей версии представлены демонстрационным интерфейсом.
7. Реальная интеграция с ГИС ЖКХ не выполняет обмен реальными данными.
8. Фотографии заявок сохраняются локально в `backend/uploads/`.
9. Для production-использования потребуется постоянное хранилище данных.
10. Секреты интеграций MAX необходимо хранить в переменных окружения или защищённом хранилище, а не в исходном коде.
